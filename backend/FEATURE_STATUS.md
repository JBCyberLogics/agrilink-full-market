## Administrator login failure findings

Two defects were reproduced and corrected. First, the provisioned administrator has an email but no username, while the old Control form labeled the identity field “Username”; the corrected UI accepts an email or username. Second, the browser API client invoked the stored native `fetch` function with the client instance as its receiver, which Chromium rejected before sending authentication or session requests. The API and CSRF calls now invoke `fetch` with `globalThis`, covered by a frontend regression test. The corrected real login form, HttpOnly session issuance, protected-route restoration, and UI logout were verified using only a temporary `agrilink_test` administrator. The existing live administrator password was not attempted, retrieved, or changed.

## Data and migration notes

- No application seed records, fake accounts, listings, orders, transactions, observations, or AI responses were added to `agrilink`.
- Automated workflow identities and listings exist only transiently in `agrilink_test` and are deleted in `finally` cleanup.
- `npm run db:init` creates the empty canonical collections and indexes without inserting application rows.
- Legacy schema inspection is read-only; `npm run db:migrate:dry-run` is isolated-database-only. No production data migration or destructive change has been applied.
- The local MongoDB data directory is persistent. Use `bash scripts/start-local-mongodb.sh` after a computer restart; do not remove the directory to reset application data.
