# AgriLink Control integration map

**Audit date:** 2026-11-12  
**Scope:** Full read-only inspection followed by controlled integration batches. Inspection did not alter live application records; source changes and isolated `agrilink_test` fixtures are documented below.

## Evidence and current environment

- The unified Express API is mounted under `/api/v1`; AgriLink Control uses `VITE_API_BASE_URL` and cookie credentials. The current workspace runtime is Farmer/Buyer Vite `http://localhost:5199`, Control Vite `http://localhost:5173`, API `http://localhost:4300/api/v1`, and MongoDB `127.0.0.1:27017`.
- MongoDB is 7.0.14 on the existing persistent data directory, configured as a one-member `agrilink-rs` replica set. The database is `agrilink`, primary is `127.0.0.1:27017`, and transaction support is available.
- Latest read-only `mongosh` inspection found 37 canonical collections, 108 indexes, and 30 documents: `users` 1, `auditlogs` 14, `refreshtokens` 9, `settings` 1, `marketdatasources` 2, and `providersyncs` 3. One active source is KAMIS and one is a generic authorized API source; three existing KAMIS syncs failed with zero accepted records. Attribution of changing live counts is uncertain. Marketplace, order, payment, and observation records remain empty. All records were preserved and no provider secret values were inspected. The live administrator has an email and no username, which caused the original UI identity-label mismatch.
- Latest public readiness response reports the database available, `aiProvider: configured`, and M-Pesa/PayPal unavailable. Configured status does not establish provider reachability or successful inference; no live NVIDIA diagnostic or inference was run.
- The existing database therefore supports the listed features, but most tables and analytics should currently render empty states. There is no live farmer, buyer, listing, order, payment, withdrawal, support, FAQ, announcement, notification, or market observation to administer. Source-management views do have the two listed records and failed sync history.
- `backend/FEATURE_STATUS.md` records passing automated tests, isolated E2E workflows, KAMIS provider retrieval/sync using `agrilink_test`, empty-data checks, and the headless Chromium route/authentication smoke completed on `agrilink_test`.
- `agrilink-frontend/README.md`, `agri_dashboard/README.md`, the Control architecture docs, proposed API contracts, and earlier implementation reports are stale. They describe an archived/absent backend and unconnected authentication, which contradict the current source and backend test evidence. There is no separate integration audit file in the workspace; `backend/FEATURE_STATUS.md` is the current status record.

### Status definitions

- **Complete and verified:** UI/service/endpoint exist and current isolated workflow evidence covers the behavior. Route-level browser acceptance is tracked separately from visual/responsive review.
- **Implemented but not integrated:** useful UI or backend capability exists, but the module does not call the intended operation or does not display the actual complete capability.
- **Partially functional:** live backend integration exists, but module actions, querying, authorization presentation, or coverage are incomplete.
- **Missing:** required administrative workflow has no working UI/API implementation.
- **Blocked by external provider configuration:** implementation exists or has a clear configuration path, but operation requires absent provider credentials or external service setup.

## Identity failure audit and implementation

The current login flow is present: `LoginForm` sends its identity value to `POST /api/v1/auth/admin/login`; the API creates a server session with an HttpOnly cookie; mutating requests obtain and send CSRF; `GET /auth/admin/session` restores the cookie session; and `POST /auth/admin/logout` revokes it. The backend supports an identity supplied as either `email` or `username`, then matches that value against `users.email` or `users.username`. The interactive `admin:create` setup asks for an email and password and stores no username.

The live administrator has an email and no username. Control originally labeled the field **Username** and instructed the operator to enter a username the provisioned account did not have. Control now labels it **Administrator email or username** and sends the identity through the backend-supported `username` field, which accepts either email or username. A second confirmed browser fault was in `AdminApiClient`: it invoked the stored native `fetch` with the client instance as `this`. Chromium rejects that receiver before sending a request, and the UI surfaced a generic network error. Both the API call and CSRF bootstrap now call the fetch implementation with `globalThis`; a regression test covers the receiver. In headless Chromium, the corrected UI form authenticated an isolated admin, received an HttpOnly cookie, restored a protected route, and logged out successfully. The actual existing live-admin credential was not attempted, retrieved, or changed; an incorrect password still cannot be ruled out without the operator's credential.

The real application defaults remain Farmer/Buyer `http://localhost:5199`, Control `http://localhost:5173`, and API `http://localhost:4300/api/v1`; these local pages and readiness endpoint returned HTTP 200. The interactive acceptance used an isolated test origin `127.0.0.1:5174` and API `127.0.0.1:4301` to keep the live application database out of test requests. Therefore the default `localhost` browser credential path and the existing administrator password still need operator-side verification.

## Cross-cutting integration findings

1. Permission-aware navigation and mutation controls are now present, while backend guards remain authoritative. The permission map mirrors each page’s endpoint permissions; the combined orders/payments route requires both read grants.
2. Administrator status uses a dedicated audited operation; generic user suspension/profile editing cannot operate on administrator accounts.
3. AI usage, on-demand provider diagnostics, matching weights/scoring, report review, and supported settings now call their purpose-built endpoints.
4. Basic permitted account information can be edited for Farmer/Buyer accounts. Listing details/moderation history, order/payment detail panels, support request/reply history with assignment, and server-side audit filters are available. Per-account activity timelines, some remaining status filters, and report export remain incomplete.
5. Reports and disputes still share the `reports` collection, and export is not implemented.
6. Security and notification settings are safe read-only diagnostics; supported platform and marketplace settings are editable with field-specific validation. Email/push and NVIDIA operation still depend on provider configuration.
7. Automated checks pass against isolated test data. Earlier Chromium visited all 34 navigation modules and verified isolated login/session/logout before final pagination and ledger-detail UI wiring. The latest browser host was unavailable, so those UI interactions were not re-walked; responsive visual review and live administrator credential verification remain pending. Latest live readiness says NVIDIA configuration is present, but no diagnostic or inference was attempted.
